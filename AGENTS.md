# memebrary development workflow

## What is generated

- `backend/pkg/api/` is generated Go server/model code. Djangolang introspects the local PostgreSQL schema and writes it.
- `backend/schema/openapi.json` is generated by the API binary at runtime.
- `frontend/src/api/api.d.ts` is generated by `openapi-typescript` from the OpenAPI schema.
- `backend/pkg/api_client/` is generated by `openapi-generator-cli` for Go-side typed calls.

The generated backend code calls generic runtime/query code from the `github.com/initialed85/djangolang` Go module. A djangolang runtime/query fix normally needs a Go dependency update and API rebuild, not schema regeneration. A djangolang template/code-generation fix needs the full workflow below.

## Prerequisites

- Go 1.26+
- Docker Compose
- Node.js 22+ / npm
- `openapi-generator-cli` (Java-based OpenAPI Generator CLI)
- `migrate` (database migration tool)

Install the OpenAPI generator CLI if missing:

```sh
npm install -g @openapitools/openapi-generator-cli@2.41.0
openapi-generator-cli version
```

## Local generation environment

For tmux/non-interactive workflows, start Compose detached and stop it explicitly:

```sh
cd backend
./run-env.sh up -d
```

`run-env.sh` pulls/builds dependencies, starts PostgreSQL (PostGIS), Redis, and runs migrations. Migrations must complete successfully before generation.

Check readiness with:

```sh
docker compose ps -a
```

Expected: `postgres` healthy, `migrate` exited 0, `post-migrate` exited 0, `redis` up. Follow logs with `./run-env.sh logs`.

Stop the stack while preserving the local PostgreSQL volume with:

```sh
./run-env.sh down
```

To intentionally reset local databases/volumes, use `./run-env.sh down --volumes`. The legacy `./run-env.sh` (no subcommand) still follows logs in the foreground and tears down containers and volumes on exit.

## Selecting djangolang

Do not blindly use `FORCE_UPDATE_DJANGOLANG=1` when a release has just been tagged: Go's module proxy may not yet list the new tag, and `@latest` can temporarily resolve to an older release.

Pin the intended release explicitly first. For example:

```sh
GOPRIVATE=github.com/initialed85/djangolang \
  go install github.com/initialed85/djangolang@v0.1.39
GOPRIVATE=github.com/initialed85/djangolang \
  go get github.com/initialed85/djangolang@v0.1.39
```

Confirm `go.mod` before generating:

```sh
grep djangolang go.mod
```

`FORCE_UPDATE_DJANGOLANG=1 ./build.sh` is useful when `@latest` is known to be correct, but it runs `go install ...@latest` and `go get -u ...@latest`; inspect the resulting `go.mod` and restore/pin it if the proxy selected an older version.

## Full generation workflow

With Compose healthy and the desired djangolang executable/module selected:

```sh
cd backend
./build.sh
```

The script:

1. Introspects PostgreSQL and regenerates `backend/pkg/api/` via djangolang.
2. Builds the local generated API binary.
3. Generates `backend/schema/openapi.json` using the running API.
4. Generates the TypeScript client and formats `frontend/src`.
5. Regenerates the Go client under `backend/pkg/api_client/`.

The script deletes and recreates generated client directories. If it fails after deletion, install the missing tool (most commonly `openapi-generator-cli`) and rerun; do not manually reconstruct generated files.

Useful flags:

- `SKIP_UPDATE_FRONTEND=1` skips `npm ci`, but still regenerates/typescripts and formats frontend source.
- `SKIP_DOCKER_COMPOSE_CHECK=1` skips only the readiness loop; it does **not** make PostgreSQL introspection unnecessary.

After generation, check that codegen fixes are present and compile:

```sh
grep -n 'UpdateField\|UpdateFields' backend/pkg/api/{meme,tag,meme_tag}.go

go test ./... -run '^$'
git diff --check
```

## Frontend development

The frontend is a Svelte 5 app using the generated OpenAPI TypeScript client (`openapi-fetch`) for read-only meme/tag data. Custom routes (uploads, ordering, AI actions, media side effects) live under `/api/custom` and are not auto-generated.

Local development:

```sh
cd frontend
npm run dev -- --host
```

Validation:

```sh
npm run check    # svelte-check: zero errors, zero warnings
npm run build    # vite production build
```

## Local full-stack development

For a complete local development cycle (migrations, generation, API + frontend running):

```sh
cd backend
./run-for-dev.sh
```

This runs migrations, regenerates the API, then starts the Go API server with Redis connectivity. Open the frontend in a separate terminal:

```sh
cd frontend
npm run dev -- --host
```

Open <http://localhost:5173>.

Set `AI_BASE_URL=` to disable vision metadata. `OPENAI_BASE_URL`, `AI_MODEL`, `OPENAI_MODEL`, and the corresponding API key aliases are also accepted.

## Runtime/deployment builds

`backend/build-tag-and-push.sh` builds and pushes both images:

```sh
cd backend
./build-tag-and-push.sh
```

The script publishes `initialed85/memebrary-backend:latest` and `initialed85/memebrary-frontend:latest` (override with `BACKEND_IMAGE` and `FRONTEND_IMAGE`). The API image runs PostgreSQL migrations before starting djangolang and stores media under `MEDIA_DIR`.

For targeted builds when only one component changed:

```sh
# Backend only
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 \
  go build -o ./tmp/api -trimpath ./cmd/api

docker build --platform=linux/amd64 \
  -t initialed85/memebrary-backend:latest -f ./docker/api/Dockerfile .
docker image push initialed85/memebrary-backend:latest

# Frontend only
docker build --platform=linux/amd64 \
  -t initialed85/memebrary-frontend:latest -f ../frontend/Dockerfile ../frontend
docker image push initialed85/memebrary-frontend:latest
```

The script pushes mutable `:latest` tags only; it does not create per-build tags. Note the backend Go module is `github.com/initialed85/membrary/backend` (one `e`) even though the images are `memebrary-*`.

## Kubernetes deployment

One target: `~/Projects/Home/home-ops/applications/memebrary-next/` → context `home-prod-next`, namespace `memebrary-next`, host `memebrary.prod.initialed85.cc`. This **is** production; the original implementation and the old `memebrary-dev`/`memebrary-last` deployments have been deleted, so roll deliberately and never re-point the ingress host without authorization.

The manifests are applied by hand (no Argo app). Apply in order when creating or changing the stack:

```sh
cd ~/Projects/Home/home-ops/applications/memebrary-next
kubectl --context home-prod-next apply -f namespace.yaml
kubectl --context home-prod-next apply -f configmap.yaml -f pvc.yaml -f postgres.yaml -f redis.yaml
kubectl --context home-prod-next apply -f backend.yaml -f frontend.yaml -f ingress.yaml
```

Topology: the backend is a single `Recreate` pod (container `backend`) because media lives on a ReadWriteOnce Longhorn PVC; metadata is in the in-namespace PostgreSQL StatefulSet with Redis for djangolang coordination; the backend image runs SQL migrations at startup. Frontend nginx (container `frontend`) serves the SPA and proxies `/api` — including `/api/custom/media` — to the in-namespace `memebrary-backend` Service.

### Rolling a new image

Both workloads use `image: initialed85/memebrary-*:latest` with `imagePullPolicy: Always`, so after a push, restart only the changed workload:

```sh
kubectl --context home-prod-next -n memebrary-next rollout restart deployment/memebrary-next-frontend
kubectl --context home-prod-next -n memebrary-next rollout status deployment/memebrary-next-frontend --timeout=300s
```

Then verify the running image actually matches what was pushed — `rollout status` succeeding does not prove it:

```sh
docker buildx imagetools inspect initialed85/memebrary-frontend:latest --format '{{.Manifest.Digest}}'
kubectl --context home-prod-next -n memebrary-next get pods -o wide
kubectl --context home-prod-next -n memebrary-next get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[0].image}{"\t"}{range .status.containerStatuses[*]}{.imageID}{"\n"}{end}{end}'
```

Public endpoints (the `/media/<id>` path is proxied to `/api/custom/media/<id>`; use a real meme ID, unknown ones 404):

```sh
curl -kfsS https://memebrary.prod.initialed85.cc/healthz
curl -kfsS https://memebrary.prod.initialed85.cc/ | grep -o 'assets/index-[^"]*\.js'   # frontend: new hash = new build live
curl -kfsS "https://memebrary.prod.initialed85.cc/api/memes?limit=1" | head -c 200      # backend: schema/API round-trip
```

Rolling the backend briefly interrupts the pod (migrations run at startup) and restarts media serving; only roll it when its code changed.

Do not modify router/network configuration as part of memebrary image rollouts.

### Known trap: digest pins leaking into the deployment

`kubectl set image <deployment> <container>=<repo>@sha256:...` writes the digest into the pod template. From then on `rollout restart` re-pulls that same old image and still reports success, and `kubectl apply` will not undo it unless the manifest says `:latest`. Keep the manifests on `:latest` and never pin digests here. If a live spec shows a digest, restore it:

```sh
kubectl --context home-prod-next -n memebrary-next set image deployment/memebrary-next-frontend \
  frontend=initialed85/memebrary-frontend:latest
kubectl --context home-prod-next -n memebrary-next rollout status deployment/memebrary-next-frontend --timeout=300s
```

## Migration to djangolang (context)

The rewrite migrated from a Go-native SQL store to djangolang's PostgreSQL ORM. Key changes:

- Cycle-safe `depth=3` relationship loading for meme→tag→meme (djangolang v0.1.39)
- Frontend switched from hand-written fetch calls to the generated OpenAPI TypeScript client (`openapi-fetch`)
- Custom endpoints under `/api/custom` remain for multipart uploads, ordering, AI actions, and media side effects

## Important notes

- `memebrary.prod.initialed85.cc` is live production for the djangolang rewrite; the pre-rewrite implementation is gone. Do not re-point the ingress host or delete the namespace/PVCs without explicit authorization.
- Media and metadata live on Longhorn PVCs in the `memebrary-next` namespace (`memebrary-next-data`, `data-memebrary-next-postgres-0`). `kubectl delete pvc`/`--volumes`-style cleanup destroys the library.
- The frontend viewer supports pinch zoom (1×–4×), shift-wheel zoom (0.25×–4×), and a fit/zoom toggle. The fit mode defaults to `true` for tall memes. Login is stored in `localStorage` as an expiry timestamp (`memebrary-authenticated-until`, 24h).
- Generated code directories (`pkg/api/`, `pkg/api_client/`, `frontend/src/api/`) are wiped and recreated by `build.sh`. Never manually edit generated files.
